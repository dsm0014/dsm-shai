# Spec 13 — Hermes Swarm Orchestration (Haiku + Qwen 9B)

> **Reconciled with spec 12 (2026-11-18):** `haiku` is not a LiteLLM alias. Every Haiku call is `/opt/jobs/claude-haiku/claude-haiku.sh` (Claude Code CLI, owner's subscription): text in, text out, no tools, no token or USD metering. Caps are call counts and the audit records calls and bytes, not tokens. Local `chat` goes through LiteLLM with the `hermes` key.

**Status:** DONE

## Purpose

Let Hermes finish tasks on its own by splitting them across a swarm of workers: Claude Haiku (via the spec 12 wrapper) for planning, judging and hard steps, and local `qwen3.5:9b` for cheap, high-volume steps. A cron template and a working example job show how to schedule such tasks. Depends on specs 04 (Hermes), 09 (LiteLLM), 11 (nightly job patterns and guardrails) and 12 (`claude-haiku.sh` wrapper).

## Behavior

**Roles and routing**
- Orchestrator: Haiku (wrapper). It decomposes a task into at most 12 steps, each tagged with a worker class, and judges results. It never edits files or runs commands itself.
- Workers: `chat` (qwen3.5:9b) by default for bounded steps (summarise, extract, draft, classify, apply a known edit); Haiku for steps tagged `hard` or after a local worker fails its verifier twice. Routing is by a deterministic script (`route.py`) from the tag and the retry count; a model never picks its own tier.
- A task may run with local workers only (`SWARM_ORCHESTRATOR=chat`) when Anthropic is unreachable or the wrapper's daily call cap is spent. This is chosen by configuration, never by an automatic fallback (spec 12).

**Concurrency and VRAM**
- The GPU runs one chat model with `max_parallel_requests: 2` (spec 09), so the local pool is capped at 2 simultaneous workers. Haiku workers are capped at `SWARM_HAIKU_PARALLEL` (default 2, which matches the wrapper's `CLAUDE_HAIKU_PARALLEL`; raising it needs the wrapper variable raised too, and `swarm.py` refuses a value above it). A scheduler script (`swarm.py`) owns the queue so a third local call is never sent and 429s are not used as flow control. Local and Haiku work run concurrently; local work never exceeds 2.
- Local worker calls go through LiteLLM with the `hermes` key; Haiku calls go through the wrapper only, with no tools (the wrapper's web research mode, spec 15, is not used by the swarm). Each step is a separate `hermes -z` call, direct LiteLLM request or wrapper call with a versioned prompt file, context under 16K tokens and a required output schema, as in spec 11.

**Task plan and state**
- A task is a YAML file with `goal`, `allowed_paths`, `max_steps`, `max_haiku_calls`, `timeout_minutes`, `verifiers`. The orchestrator writes a plan JSON (steps, dependencies, worker class), validated against a schema before any worker starts. An invalid plan is retried once, then the task fails.
- State lives under `/opt/data/swarm/runs/<run-id>/` (plan, per-step input and output, verifier results). Steps with no dependency between them run in parallel within the caps above; a step starts only when its dependencies passed their verifiers.
- Fetched and generated content is untrusted: prompts wrap it in delimiters, and worker output is only accepted through the verifier and the path allowlist.

**Verification and autonomy limits**
- Each step has a non-LLM verifier (schema parses, file exists, diff within `allowed_paths` and line caps, tests exit 0). Only verifier results count as success. A failed step retries once on the same tier, once on the next tier (`chat` then `haiku`), then fails the task and discards uncommitted work.
- Hard caps, enforced by scripts and by the wrapper's own daily call cap (`CLAUDE_HAIKU_DAILY_CALLS`, shared with every other Haiku caller): steps per task, Haiku calls per task (`max_haiku_calls`), wall-clock timeout (`timeout`), at most one running swarm per task name (`flock`). Reaching any cap ends the task with status `capped` and a digest line, never a retry loop.
- Workers have no new credentials: no kubectl, no GitHub token unless the task file lists it, no write outside `allowed_paths`. Egress is unchanged from spec 11 (GitHub hosts only, through the proxy); Anthropic is reached only through the wrapper. A task names its target repo and `swarm.py` refuses any repo not in `SWARM_ALLOWED_REPOS` (default: none), so a broad GitHub token cannot widen a task's reach (same fail-closed rule as spec 11's `NIGHTLY_REPO`).
- Audit: append-only JSONL `/opt/data/swarm/audit.jsonl` with run ID, task, per-step worker, tier, verifier result, calls, input and output bytes and duration per model (local token counts from LiteLLM spend for key `hermes`; Haiku tokens and cost are not metered on a subscription), plus a one-line summary `remember` into OpenViking. Metrics `swarm_last_success_timestamp`, `swarm_last_run_status` and `swarm_haiku_calls_total` are served read-only and scraped by Prometheus (spec 06).
- Kill switches: `hermes pause`, a `/opt/data/swarm/disabled` flag file checked before each run, the wrapper's `disabled` flag (`/opt/data/claude-haiku/disabled`), which stops every Haiku call and makes the task fall to `capped`.

**Make interface (root `Makefile`, same style as the `nightly-*` targets; each target has a `##` help line)**
- `make swarm-preflight`: check the tools, state directory, `claude-haiku.sh --preflight`, `chat` reachability through LiteLLM, and that the Haiku daily call cap is not spent.
- `make swarm-plan TASK=<name>`: the dry run; builds and prints the plan, makes no worker call, spends nothing.
- `make swarm-run TASK=<name>`: runs the task in the pod in the background with a log under `/opt/data/swarm/`. `TASK` is a name under `deploy/hermes/jobs/` (default `swarm-example`) or a path to a task YAML. Tasks that write outside the state directory need `CONFIRM=1`, as `nightly-run` does. `SWARM_ORCHESTRATOR=chat` and `SWARM_HAIKU_PARALLEL=<n>` pass through as variables.
- `make swarm-status`: running or not, last audit entries, digest lines, metrics, and Haiku calls used today against the daily cap.
- `make swarm-stop`: stops the running swarm cleanly (releases the lock); `make swarm-test`: the offline tests (fake gateway, no cluster needed). `make hermes-pause` stays the emergency stop.
- A missing or unknown `TASK` prints usage and exits 2; the targets work from the repo root with no extra setup.

**Hermes cron template and example**
- `deploy/hermes/jobs/swarm-template/` holds a documented template: `task.example.yaml`, `run.sh` (flock, timeout, state dir, calls `swarm.py`), `register-cron.sh` (prints the `hermes cron create ... --paused` command with a schedule placeholder, same convention as spec 11), and a README of every field.
- `deploy/hermes/jobs/swarm-example/` is a runnable instance of the template: a daily "repo digest" task (nightly or on demand) that reads a configured public repo, uses local workers to summarise each changed file, uses a Haiku step to merge the summaries into one report, and stores it in OpenViking. It writes no files outside its state directory, so it is safe to run unattended.
- Both are registered paused. A `--dry-run` mode builds and prints the plan, calls no worker and spends nothing.
